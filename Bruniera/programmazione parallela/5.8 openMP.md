# OpenMP

Open Multi Processing

È più ad alto livello di pthread, e non serve usare esplicitamente mutex e cond variables. Invece è basato su direttive di compilazione. Usando le direttive si indicano sezioni di codice da eseguire in parallelo, e il compilatore inserirà il codice per farle eseguire da team di thread.

Non è una libreria ma un estensione del linguaggio (come CUDA). È disponibile per C, C++, e Fortran, e stanno lavorando a Python. Di questi linguaggi supporta un'ampia varietà di compilatori.

È lo standard de facto per HPC e calcolo scientifico. Ha un ottima portabilità.

## Programming model

Il programmatore indica al compilatore quali parti del codice devono essere eseguite da più thread, ed il compilatore si occupa di gestire i thread e sincronizzarli.

Il compilatore può applicare varie ottimizzazioni, anche dipendenti dall'architettura.

In generale il codice parallelo e seriale è lo stesso o comunque con minime differenze. Questo consente di scrivere il programma seriale prima e parallelizzarlo incrementalmente.

Le direttive OMP sono indicate con la direttiva `#pragma` di C/C++. In generale hanno la forma `#pragma omp <direttiva> [<clausole>]`.

## Direttiva parallel

Indica una sezione di codice da eseguire in parallelo.

Esempio:

```c
#include <omp.h>
#include <stdio.h>

int main(void) {
  printf("codice seriale\n");
#pragma omp parallel num_threads(6) // altro...
  {
    printf("Codice parallelo eseguito da %d thread\n",

           omp_get_num_threads());

    if (omp_get_thread_num() == 2) {

      printf("Il thread %d fa cose diverse\n",

             omp_get_thread_num());
    }

    printf("Sono il thread %d\n", omp_get_thread_num());
  }
  printf("ancoda codice seriale\n");
  return 0;
}
```

> [!IMPORTANT]
> Fare jump dentro o fuori dal blocco è undefined behaviour

<!--questo commento serve a spezzare le quotes-->

> [!IMPORTANT]
> L'ordine di esecuzione è non deterministico. Non bisogna farci affidamento

Compila con `gcc -fopenmp ...`.

Le possibili clausole sono:

* `if(expression)`: se la condizione è falsa, l'esecuzione è seriale (ce ne può essere solo una)
* `num_threads(integer-expression)`: specifica il numero di thread da eseguire in parallelo, se non specificato viene scelto in automatico (ce ne può essere solo una)
* `private(list)`: specifica le variabili che in questo blocco sono thread-local. All'inizio del blocco sono uninitialised
* `firstprivate(list)`: come private, ma inizializza le variabili col valore che avevano prima di entrare nel blocco
* `shared(list)`: specifica le variabili condivise tra i thread. Possono avere race conditions
* `default(none|shared)`: specifica il comportamento di default delle variabili non esplicitamente dichiarate
  * `default(shared)`: tutte shared (è anche il comportamento di default)
  * `default(none)`: devono essere esplicitate tutte
  * le altre varianti (`default(private)` e `default(firstprivate)`) sono state aggiunte tardi
* `copyin(list)`: vedremo dopo
* `reduction(operator:list)`: esegue una riduzione alla chiusura del blocco.
  * esempio: `reduction(+: sum)` fornisce a tutti i thread la variabile privata `sum`, e al termine vengono combinate tutte con `+`

La direttiva parallel può essere combinata con altre direttive per distribuire il lavoro tra i thread (work-sharing).

## Work sharing

### Direttiva for

Specifica che le iterazioni di un for loop devono essere ripartite tra i thread del team.

Si assume che le iterazioni del for siano indipendenti. Alla fine del for viene inserita una barriera.

Il mapping tra thread e iterazioni è arbitrario.

Esempio:

```C
int main(void) {
  long sum = 0, npoints = 1000000;
  double rand_no_x, rand_no_y, points_per_thread, num_threads;

#pragma omp parallel private(rand_no_x, rand_no_y, num_threads,                \
                                 points_per_thread) shared(npoints)            \
    reduction(+ : sum) num_threads(8)
  {
    sum = 0;
    unsigned int seed = 9 + omp_get_thread_num();
#pragma omp for
    for (int i = 0; i < npoints; i++) {
      rand_no_x = (double)(rand_r(&seed)) / (double)RAND_MAX;
      rand_no_y = (double)(rand_r(&seed)) / (double)RAND_MAX;
      if (((rand_no_x - 0.5) * (rand_no_x - 0.5) +
           (rand_no_y - 0.5) * (rand_no_y - 0.5)) < 0.25)
        sum++;
    }
  }

  printf("result: %ld\n", sum);
  printf("Estimated Pi: %f\n", 4.0 * (double)sum / (double)npoints);

  return 0;
}
```

> [!NOTE]
> Ignorando le direttive si ottiene un codice seriale equivalente.
>
> Senza la direttiva `for` non sarebbe così, ma servirebbe cambiare gli estremi del for

Alcune regole per la direttiva for:

* *deve* essere seguita da un `for(initexp; var relop val; increxp)`
* il numero di iterazioni deve essere noto all'inizio del loop
* `initexpr`, `increxpr`, e il test devono essere invarianti
* `initexpr` e `val` devono essere espressioni intere
* `relop` deve essere una tra: `<`, `>`, `<=`, `>=`
* `increxpr` deve usare uno tra: `--`, `++`, `+=`, `-=`, oppure essere nella forma `var=var+incr`
* `var` non deve essere modificata nel corpo del loop

Le clausole possibili sono:

* `private(list)`: ...
* `firstprivate(list)`: ...
* `shared(list)`: ...
* `reduction(operator:list)`: ...
* `lastprivate(list)`: all'uscita dal blocco, assume il valore della variabile nell'ultima iterazione
* `schedule(scheduling_class[,chunksize])`: definisce come assegnare le iterazioni nel loop
  * `schedule(static,chunksize)`: sono partizionate in chunk di `chunksize`, ed i chunk sono assegnati in round-robin
  * `schedule(dynamic,chunksize)`: sono partizionate in chunk di `chunksize`, ed i chunk sono assegnati man mano che i thread si liberano
  * `schedule(auto)`: decide il compilatore o la runtime
  * `schedule(guided,chunksize)`: `chunksize` indica la dimensione minima, i chunk sono assegnati man mano che i thread si liberano, e il chunk assegnato è di dimensione `rimanenti/thread`, si rimpiccioliscono man mano fino a un minimo di `chunksize`. L'ultimissimo chunk può essere più piccolo
  * `schedule(runtime)`: segue la variabile d'ambiente `OMP_SCHEDULE`
* `nowait`: non inserire la barriera alla fine del loop
  * utile quando si hanno due for indipendenti consecutivi
* `ordered`: *vedremo più avanti*. Indica che nel for viene usata la direttiva `ordered`
  * è importante, aiuta ad esempio nelle prefix sum
* `collapse(n)`: associa `n` loop innestati alla stessa direttiva for

### direttiva sections

Mentre la direttiva for ripartisce iterazioni tra i thread, `sections` ripartisce task che non corrispondono ad un loop.

```C
#pragma omp sections [clause list]
{
    [#pragma omp section
        { /* blocco di codice C */ }
    ]
    [#pragma omp section
        { /* blocco di codice C */ }
    ]
    ...
}
```

Ogni section viene assegnata ad un thread, e potenzialmente più section allo stesso thread. Il mapping è arbitrario, e viene introdotta una barriera alla fine del blocco (eccetto `nowait`). Saltare dentro o fuori dalle section non è ammesso

### Merging

È possibile unire alcune direttive innestate in un unica direttiva per semplificare il codice.

Esempio:

```C
#pragma omp parallel for shared(n)
{
  for (i=0; i<n; i++) {
    /* corpo del for */
  }
}
```

## Direttiva threadprivate

Le variabili globali sono shared di default nei blocchi parallel. La direttiva `threadprivate` le rende private.

```C
int a, b, c;
#pragma omp threadprivate(a, b)
```

Tutte le variabili elencate nella direttiva diventano private per thread. Inoltre, mantengono il loro scope globale, quindi sono persistenti.

Per usare queste variabili bisogna rispettare due vincoli:

* due sezioni parallele che accedono alla stessa variabile devono avere lo stesso numero di thread
* le sezioni parallele non devono essere annidate

### La clausola copyin

Viene impiegata per inizializzare le variabili `threadprivate`.

Di default, le variabili threadprivate sono presenti in ogni thread ma non inizializzate. Aggiungendo la clausola `copyin(list)` al blocco parallel, le variabili vengono inizializzate col valore che avevano prima di entrare nella sezione parallela.

## Sincronizzazione

### Direttiva barrier

La forma generale è `#pragma omp barrier`. Introduce una barriera esplicita per il team di thread attivo.

### Direttiva single

La forma generale è `#pragma omp single [clause list]`. Viene posizionata prima di un blocco, che verrà eseguito da un solo thread del team attivo. Al termine del blocco viene inserita una barriera implicita. È utile per inizializzazioni di risorse condivise.

Le clausole sono:

* `private(list)`: ...
* `firstprivate(list)`: ...
* `copyprivate(list)`: al termine del blocco, manda in broadcast il valore di alcune variabili private agli altri thread del team
* `nowait`: inibisce la barriera, non si può usare con `copyprivate`

### Direttiva master

Indica un blocco che viene eseguito solo dal thread `0`.  A differenza di `single` non ha una barriera implicita alla fine.

### Direttiva critical

Indica una sezione critica da eseguire in mutua esclusione.

```C
#pragma omp critical [(name)]
  { /* blocco di codice C */ }
```

Sono in mutua esclusione tutti i blocchi con lo stesso `name`.

Esempio:

```C
#pragma omp parallel sections
  {
    #pragma omp section
      { /* produttore */
        item = produce_item();
        #pragma omp critical (accessocoda)
          {
            inserisce_in_coda(item);
          }
      }
    #pragma omp section
      { /* consumatore */
        #pragma omp critical (accessocoda)
          {
            preleva_da_coda(item);
          }
        consuma_item(item);
      }
  }
```

### Direttiva atomic

Realizza accessi atomici a dei dati.

```C
#pragma omp atomic [read|write|update|capture]
/* singola istruzione di assegnamento */
```

Si può applicare solo a semplici istruzioni di assegnamento. L'implementazione può essere con istruzioni hardware specifiche o emulata come una sezione critica.

Clausole (in tutti gli esempi è garantito l'accesso atomico solo ad `x`):

* `read`: l'istruzione deve essere nella forma `y = x`
* `write`: l'istruzione deve essere nella orma `x = expr` dove `expr` non accede ad `x`
* `update`: l'istruzione deve essere in una delle seguenti forme
  * `x = x OP expr` dove `expr` non accede ad `x`, e `OP` è un operatore tra `+`, `-`, `*`, `/`, `&`, `^`, `|`, `<<`, e `>>`
  * `x OP= expr`  dove `expr` non accede ad `x`, e `OP` è uno degli operatori precedenti
  * `x++` o `x--`
* `capture`: l'istruzione deve essere nella forma `v = UPDATE(x)` dove `UPDATE(x)` è un aggiornamento della variabile `x` in una delle forme precedenti
  * viene aggiornata la variabile `x`, ed il suo valore precedente è memorizzato in `v`

Non tutte le versioni di OMP supportano tutte le clausole.

Com'è il memory ordering? Non è spiegato. Probabilmente il livello massimo.

### Direttiva ordered

Indica che una sezione di codice parallelo deve essere eseguita come se i thread eseguissero in ordine sequenziale. In tipicamente si usa con `parallel for`, che possiede una clausola `ordered` per informare il compilatore che verrà utilizzata la direttiva `ordered` da qualche parte nel corpo del for.

Supponiamo di avere un ciclo for che vogliamo parallelizzare, ma l'esecuzione è dipendente dall'ordine delle iterazioni. Dovremo parallelizzarlo mantenendo l'ordine almeno in alcune parti critiche del codice. Questo è lo scopo della direttiva.

Esempio (prefix sum):

```C
psum[0] = dati[0] = 0;
#pragma omp parallel for private(i) \
shared(psum,dati,n) ordered
for (int i=1; i<n; i++) {
  /* codice che calcola i valori dei dati[i]
  assumendo indipendenti tali computazioni */
  #pragma omp ordered
    { /* parte eseguita come se fosse seriale */
      psum[i] = psum[i-1] + dati[i]; 
    }
}
```

Un altro uso tipico è per stampare da una sezione parallela in modo ordinato:

```C
#pragma omp parallel for private(i)
for (i=1; i<n; i++) {
  /* codice che calcola i valori
  dei dati[i] in parallelo*/
  #pragma omp ordered
    { /* parte eseguita come se fosse seriale */
      printf("il dato %i-esimo: %d\n", i, dati[i]);
    }
}
```

## Extra

### Nesting

Si possono annidare le direttive `parallel`.

Per le sezioni parallele interne:

* se il nested parallelism è abilitato, OMP avvierà un nuovo team
* se è disabilitato, il lavoro viene spartito tra i thread del team esistente

Per abilitare/disabilitare si usa `omp_set_nested`.

Non tutte le implementazioni supportano nesting, e può causare un degrado delle performance (per overhead).

Si può controllare il massimo livello di nesting con `omp_set_max_active_levels`.

Le barrier influenzano solo il livello più interno, invece le direttive `critical` e `atomic` riguardano tutti i thread.

### Direttiva flush

È una sorta di memory fence. Serve a rendere tutte le modifiche delle variabili shared visibili a tutti i thread.

Di per se, le variabili vengono flushed ad ogni punto di sincronizazione (e.g. barriere), però è possibile forzare il flush con questa direttiva.

```C
#pragma omp flush [list]
```

Se la lista di variabili è omessa, si applica a tutte.

Se un thread *non ha* modificato la variabile "riceve" il valore dagli altri thread. Se un thread *ha* modificato la variabile, publica la modifica.

Non implica sincronizzazione.

> [!IMPORTANT]
> Gli atomic non implicano un flush di tutte le variabili, solo della variabile atomica stessa
> Se stai usando gli atomic per (ad esempio) uno spin lock, devi aggiungere un flush prima o dopo l'atomic

### I lock

OMP fornisce anche delle regolari lock variables.

Possono essere di due tipi:

* `omp_lock_t`: semplici lock, come i mutex
* `omp_nest_lock_t`: lock annidabili, allo stesso thread è concesso di loccare la stessa variabile più volte

Sono dei costrutti di basso livello e possono causare deadlock.

Le funzioni sui lock sono:

* `omp_init_lock`: equivalente di `pthread_mutex_init`
* `omp_set_lock`: equivalente di `pthread_mutex_lock`
* `omp_test_lock`: equivalente di `pthread_mutex_trylock`
* `omp_unset_lock`: equivalente di `pthread_mutex_unlock`
* `omp_destroy_lock`: equivalente di `pthread_mutex_destroy`

Nel caso dei lock nestabili, settarlo più volte incrementa un contatore, mentre unsettarlo lo decrementa. Il lock è rilasciato quando il contatore è azzerato.

## Task parallelism

Sono un meccanismo simile ad `async`.

In alcuni casi, non è agevole esprimere i task con il costrutto parallel. In quei casi si può usare la direttiva `task`, che permette di definire dei compiti che verranno eseguiti in parallelo.

Un task viene definito da un thread ed è composto da codice, ambiente ed esecutore. Inoltre, un task può definire altri task ricorsivamente.

Un task può essere undeferred (eseguito immediatamente) oppure deferred (eseguito in ritardo). La decisione è a runtime.

```C
#pragma omp task [clause list]
  { /* blocco di codice */ }
```

Quando all'interno di un parallel, un thread raggiunge la direttiva `task`, il blocco di codice diventa un task che può essere eseguito immediatamente o inserito in un pool di task. Poi il thread prosegue col resto del codice.
Quando il thread raggiunge una barrier, prosegue con i task nel pool.

Le clausole sono:

* `if(...)`: ...
* `private(...)`: ...
* `firstprivate`(...): ...
* `shared(...)`: ...
* `default(...)`: ...
* `untied`: indica che il task è *untied* (se assente è *tied*)
  * **tied**: il task può essere continuato solo dal thread che lo definisce
  * **untied**: il task può essere continuato da un altro thread
* `final(expr)`: se expr è true, il task è *finale*
  * un task finale esegue immediatamente i task che definisce, come fosse codice normale
  * i task definiti da un task finale sono anch'essi finali
  * è simile alla clausola `if` ma:
    * `if` non influenza i sotto-task
    * il booleano è invertito
* `depend(tipo-dipendenza:locator-list)`: indica che il task accede a delle locazioni, l'informazione viene usata da OMP per ordinare e schedulare i task
  * locazioni:
    * `var`: accede alla variabile `var`
    * `arr[N]`: accede alla cella `N` di `arr`
    * `arr[N:M]`: accede alle celle da `N` a `M`
    * ...
  * tipo:
    * `in`: accede in sola lettura
      * può eseguire parallelamente ad altre letture, ma non scritture
      * deve aspettare tutte le scritture definite in precedenza
    * `out`: accede in sola scrittura (overwrite)
      * aspetta tutti i task definiti in precedenza
      * non esegue parallelamente ad altre scritture o letture (sulle stesse locazioni)
    * `inout`: accede in lettura e scrittura
      * identico ad `out`
      * serve per leggibilità
    * ...

### Direttive taskwait e taskgroup

Servono per attendere il completamento dei task.

Di base, un task può essere sospeso e riattivato in qualsiasi task scheduling point (tipo le promises).

Per i task `tied`, gli scheduling point sono nelle barriere, alla fine dei blocchi, alla generazione dei task, etc.

Per i task `untied` qualsiasi punto è uno scheduling point.

Un task può anche sospendersi per attendere i task che ha generato. Lo fa con queste direttive:

* `taskwait`: attende i figli *diretti*
* `taskgroup`: attende tutti i discendenti, anche indiretti

### Direttiva taskloop

```C
#pragma omp taskloop [clause list]
  for (...) {
    /* body */
  }
```

Permette di definire dei task corrispondenti alle iterazioni di un for. L'ordine di definizione (ed esecuzione) non è specificato.

Le clausole sono:

* `if`: ...
* `private`: ...
* `firstprivate`: ...
* `shared`: ...
* `lastprivate`: ...
* `default`: ...
* `reduction`: ...
* `collapse`: ...
* `untied`: ...
* `grainsize(n)`: limita il numero di iterazioni per task ad un valore tra `n` e `2n`
* `num_tasks(n)`: limita il numero massimo di task, le iterazioni sono divise equamente
  * non può essere usato con `grainsize`

## Vettorizzazione

OMP permette di convertite i loop in operazioni vettoriali mediante la direttiva `simd`

```C
#pragma omp simd [clause list]
  for (...) {
    /* body */
  }
```

Il numero di iterazioni eseguite parallelamente dipende dall'implementazione. Un gruppo di iterazioni concorrenti è chiamato *simd chunk* (sono tipo i warp).

I simd chunk sono distribuiti tra i thread del team.

Le clausole sono:

* `if`: ...
* `private`: ...
* `lastprivate`: ...
* `reduction`: ...
* `collapse`: ...
* `safelen(costante)`: la massima "distanza" tra due iterazioni nello stesso chunk
  * in pratica, il massimo numero di iterazioni che sono indipendenti
* `simdlen(costante)`: specifica il numero di iterazioni in un'iterazione concorrente (warp width)
* `aligned(list:alignement)`: specifica l'allineamento (in byte) delle liste
  * `list`: uno o più puntatori o array
  * `alignement`: una potenza di 2
  * permette al compilatore di generate istruzioni che rispettano l'allineamento (per performance)

## Device e target

OMP permette di programmare sistemi eterogenei (host e target devices). I devices sono *esecutori* e sono *dotati di memoria*.

Alcune funzioni:

* `int omp_get_num_devices()`: restituisce il numero dei devices
* `int omp_get_default_device()`: il device default
* `void omp_set_default_device(int dev_num)`: imposta il device
* `int omp_get_device_num()`: il device su cui il chiamante sta eseguendo
* `int omp_get_initial_device()`: l’host

La direttiva `target` determina una sezione di programma da caricare su un device. Di default, la sezione target è eseguita synchronously (l'host attende la terminazione).

Host e devices hanno spazi di indirizzi diversi, i dati devono essere mappati. Di default:

* **dati scalari**: sono trattati come `firstprivate` (dipende dalla versione)
  * come degli uniform o come argomenti dei kernel
* **array statici**: copiati sul device all'inizio, e scaricati al termine della computazione
  * come con due memcpy
* ...

Le clausole della direttiva sono valutate quando viene raggiunta la direttiva, ma le copie per il mapping avvengono all'esecuzione

Alcune delle clausole sono:

* `device(intero)`: specifica l'indice del device che eseguirà il blocco
* `map(type:loclist)`: specifica il mapping di alcune locazioni
  * `loclist`: una lista di locazioni (vedi la clausola `depend` dei task)
  * `type`: il tipo di mapping
    * `to`: host to device all'inizio
    * `from`: device to host alla fine
    * `tofrom`: entrambi i precedenti
    * `alloc`: alloca spazio per una copia, ma senza copia
    * ...

In linea di principio, in una sezione target si possono usare tutte le direttive viste finora. Tuttavia, l'effettivo supporto dipende da come il device implementa il parallelismo.

Esempio (sbagliato):

```C
#pragma omp target map(to:X[0:N],Y[0:N]), map(tofrom:Res)
{
  #pragma omp parallel for reduction(+:Res)
    {
      for (int i=0; i<N; i++) {
        Res = Res + X[i] + Y[i];
      }
    }
}
```

Questo *può* essere usato su una GPU, *ma* usa un solo SM, quindi non è ottimale. Però potrebbe essere adeguato su altri device.

### Direttiva teams

La direttiva `teams` permette di creare una collezione di thread master, ciascuno sarà il master di un gruppo di thread. Tipicamente, ciascuno genera un team di thread.

Questi team hanno lo stesso numero di thread e non sono sincronizzati.

Hmmm, suonano molto come i thread blocks di CUDA...

```C
#pragma omp target
  #pragma omp teams
    #pragma omp parallel
      { ... }
```

### Direttiva distribute

Permette di distribuire le iterazioni di un for loop tra i diversi teams e thread di ogni team in un device.

```C
#pragma omp target teams distribute parallel for \
        map(to:X[0:N],Y[0:N]), map(tofrom:Res) \
        reduction(+:Res)
  {
    for (int i=0; i<N; i++) {
      Res = Res + X[i] + Y[i];
    }
  }
```

Questo codice somma tutti i valori di due vettori su una GPU.

Alcune clausole:

* `dist_schedule(static,chunksize)`: permette di specificare la dimensione dei chunk di iterazioni
* `collapse`: ...
  * rende più facile distribuire il lavoro tra gli SM
  * insieme a `chunksize=1` favorisce coalescing

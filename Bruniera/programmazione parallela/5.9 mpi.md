# MPI

Message Passing Interface

## Sistemi di message passing in generale

I sistemi a scambio di messaggi sono caratterizzati da due principi:

* spazio di indirizzamento partizionato
* parallelizzazione esplicita

Logicamente, l'hardware appare come N processori, ciascuno con la sua memoria. Ogni dato appartiene ad un processore e risiede nel suo spazio. Per condividere interagire tra i processi (condividere dati) serve cooperazione da parte di entrambi (invio e ricezione di messaggi). Bisogna favorire la località degli accessi per ridurre la complessità.

I due principali paradigmi sono:

* **asincrono**: tutti i task concorrenti procedono in modo asincrono
  * potenziali race condition
* **debolmente sincrono**: i task sono sincronizzati solo nella parte che deve interagire
  * il resto è asincrono, ma senza rischio di race conditions (non ci sono interazioni)

In generale, ogni task può svolgere operazioni interamente arbitrarie, quindi l'opposto di SIMD e SIMT. Spesso però si segue un approccio SPMD (single program multiple data), ovvero i task eseguono lo stesso codice su dati diversi, ma con possibilità di divergere arbitrariamente nell'esecuzione.
Comunemente, alcuni dei processi svolgono un ruolo di controllo ed eseguono un codice diverso dagli altri.

Le operazioni fondamentali sono:

* `send(void *buffer, int numElem, int destinazione)`: invio
* `receive(void *buffer, int numElem, int sorgente)`: ricezione

Esempio:

```C
P0:
  int a = 100;
  send(&a, 1, P1);
  a = 0;

P1:
  int a;
  receive(&a, 1, P0);
  printf("%d\n", a);
```

### Send e receive bloccanti

La `send` bloccante impone che l'invio termini quando è garantita la semantica. Non implica attendere il completamento di `receive`.

Le operazioni possono essere:

* **unbuffered**: `send` deve attendere che sia eseguita la `receive`
  * serve una handshake per iniziare l'invio
  * serve un acknowledgement della ricezione
  * può causare deadlock
  * la sincronizzazione può essere inefficiente
* **buffered**: permettono di evitare i deadlock, e possono essere realizzate con o senza hardware
  * con supporto hardware
    * all'inizio della send i dati sono copiati in un buffer e la send termina
    * modificare i dati successivamente non modifica i dati condivisi
    * l'hardware copia i dati dal buffer del mittente a quello del destinatario
    * quando il destinatario esegue `receive` controlla se nel buffer ci sono dati, in quel caso li copia nella sua memoria, altrimenti attende
  * senza supporto hardware
    * si può usare un solo buffer
    * quando inizia la `send` il destinatario viene interrotto
    * entrambi i processi partecipano al trasferimento, copiando i dati nel buffer del destinatario
    * quando il destinatario esegue `receive` copia i dati dal buffer, se ci sono, altrimenti attende
    * è possibile scambiare i ruoli
  * non escludono completamente i deadlock

Esempio di deadlock con operazioni unbuffered:

```C
P0:
  send(&a, 1, P1);
  receive(&b, 1, P1);

P1:
  send(&a, 1, P0);
  receive(&b, 1, P0);
```

Esempio di deadlock con operazioni buffered:

```C
P0:
  receive(&a, 1, P1);
  send(&b, 1, P1);

P1:
  receive(&a, 1, P0);
  send(&b, 1, P0);
```

### Send e receive non bloccanti

Le operazioni non bloccanti restituiscono subito il controllo al processo, che può continuare la computazione. Viene delegato al programmatore il compito di garantire la correttezza (e.g. evitando di modificare i dati prima che vengano trasferiti).

Si solito si fornisce un operazione `check_status` per verificare se la comunicazione è stata completata.

Anche qua le operazioni possono essere:

* **buffered**
  * i dati sono copiati in un buffer mentre il mittente prosegue l'esecuzione
  * quando si esegue la receive si effettua il trasferimento
  * senza supporto hw:
    * la send chiede di trasferire i dati
    * la receive accetta la richiesta
    * entrambi partecipano
  * con supporto hw:
    * i due processi proseguono anche durante il trasferimento
    * i due processi devono evitare di leggere/modificare i dati durante il trasferimento
* **unbuffered**: ?

## Introduzione MPI e funzioni principali

È uno standard introdotto per fornire una base comune per la programmazione a scambio di messaggi.
Definisce una libreria C/Fortran, e la sintassi e semantica delle operazioni. Esistono varie implementazioni (MPICH, OpenMPI, LAM-MPI, MESH-MPI, ...).

Lo standard definisce centinaia di funzioni, ma le principali sono 6:

* `MPI_Init(int *argc, char **argv)`: inizializza MPI
  * ogni processo deve inizializzare MPI prima di qualsiasi altra chiamata MPI
  * `argv` e `argc` sono gli stessi del `main`
  * la funzione modificherà `argv` e `argc` (e.g. rimuovendo le opzioni specifiche per MPI)
* `MPI_Finalize()`: termina MPI
  * al termine, tutti i processi devono chiamare finalize, non si possono più fare altre chiamate MPI
* `MPI_Comm_size()`: determina il numero dei processi
* `MPI_Comm_rank()`: determina l’identità del processo
* `MPI_Send()`: spedisce un messaggio
* `MPI_Recv()`: riceve un messaggio

Tutte le funzioni restituiscono `MPI_SUCCESS` oppure un codice di errore.

### Communicators

Un insieme di processi che comunicano forma un *communication domain*. Le informazioni sul domain sono memorizzate in variabili dette *communicators*, di tipo `MPI_Comm`. Un communicator identifica univocamente un insieme di processi, e deve essere specificato in ogni operazione.

`MPI_COMM_WORLD` è il communicator di default.

Ogni processo può appartenere a più domain. Si possono definire domain aggiuntivi

* `int MPI_Comm_size(MPI_Comm comm, int *size)` scrive su `size` il numero di processi nel domain
* `int MPI_Comm_rank(MPI_Comm comm, int *rank)` scrive su `rank` il rank del processo chiamante
  * un rank identifica univocamente un processo in un dominio

Si possono chiamare solo se il processo chiamante appartiene a `comm`.

### Hello world

```C
#include <mpi.h>

main(int argc, char *argv[]) {
  int tutti, myrank;
  MPI_Init(&argc, &argv);
  MPI_Comm_size(MPI_COMM_WORLD, &tutti);
  MPI_Comm_rank(MPI_COMM_WORLD, &myrank);
  printf("Hello World! dal processo %d (siamo in %d)\n",
         myrank, tutti);
  MPI_Finalize();
}
```

I comandi di compilazione ed esecuzione dipendono dall'implementazione. Con OpenMPI sono:

```sh
mpicc helloworld.c -o helloworld
mpirun --oversubscribe -np 4 helloworld
```

`--oversubscribe` esegue più processi sullo stesso nodo.

### Funzione send

```C
int MPI_Send(void *buf, int count, MPI_Datatype datatype,
             int dest, int tag, MPI_Comm comm)
```

Invia i dati puntati da `buf`. `datatype` e `count` identificano la dimensione del buffer da inviare. Il destinatario è identificato dal rank (passato a `dest`) e dal dominio (`comm`).

Ogni messaggio ha un `tag`. Indicato da un integer compreso tra `0` e `MPI_TAG_UB`. Il datatype deve essere scelto tra quelli forniti da MPI, che corrispondono ai tipi C.

| Tipo MPI             | Tipo C               |
| -------------------- | -------------------- |
| `MPI_CHAR`           | `signed char`        |
| `MPI_SHORT`          | `signed short int`   |
| `MPI_INT`            | `signed int`         |
| `MPI_LONG`           | `signed long int`    |
| `MPI_UNSIGNED_CHAR`  | `unsigned char`      |
| `MPI_UNSIGNED_SHORT` | `unsigned short int` |
| `MPI_UNSIGNED`       | `unsigned int`       |
| `MPI_UNSIGNED_LONG`  | `unsigned long int`  |
| `MPI_FLOAT`          | `float`              |
| `MPI_DOUBLE`         | `double`             |
| `MPI_LONG_DOUBLE`    | `long double`        |
| `MPI_BYTE`           | singolo byte         |
| `MPI_PACKED`         | dati packed          |

### Funzione receive

```C
int MPI_Recv(void *buf, int count, MPI_Datatype datatype,
             int src, int tag, MPI_Comm comm,
             MPI_Status *status)
```

`count` indica la massima quantità di dati che si può ricevere. Bisogna indicare esplicitamente i mittenti e i tag che intendiamo ricevere. Esistono le costanti `MPI_ANY_SOURCE` e `MPI_ANY_TAG` per ricevere qualsiasi messaggio. La variabile `status` viene usata per controllare l'esito dell'operazione.

```C
typedef struct MPI_Status {
  int MPI_SOURCE; // source del messaggio ricevuto
  int MPI_TAG;    // tag del messaggio ricevuto
  int MPI_ERROR;  // eventuale codice di errore
};
```

```C
int MPI_Get_count(MPI_Status *status,
                  MPI_Datatype datatype, int *count)
```

Questa funzione recupera il numero di elementi effettivamente ricevuti. Può essere inferiore a quanto passato a `recv`.

### Dettagli su send e receive

Receive è sempre bloccante, restituisce il controllo solo dopo aver ricevuto il dato.

Send può essere in due modi:

* termina quando la receive è iniziate ed il messaggio spedito
* copia in un buffer e termina senza aspettare

In entrambi i casi `buf` è riutilizzabile quando send termina.

I programmi devono essere scritti per funzionare indipendentemente da questa differenza

### Esempio good 1

```C

int main(int argc, char **argv) {
  MPI_Init(NULL, NULL); // non uso argc e argv
  int rank, size;
  MPI_Comm_rank(MPI_COMM_WORLD, &rank);
  MPI_Comm_size(MPI_COMM_WORLD, &size);
  int number;
  if (rank == 0) { // processo che spedisce
    number = -123; // messaggio di tipo int
    MPI_Send(&number, 1, MPI_INT, 1, 0, MPI_COMM_WORLD);
  } else if (rank == 1) { // destinatario
    MPI_Recv(&number, 1, MPI_INT, 0, 0, MPI_COMM_WORLD,
    MPI_STATUS_IGNORE); // ignora lo status
    printf("Ho ricevuto %d\n", number);
  }
  MPI_Finalize();
}
```

### Esempio bad 1

```C
int a[10], b[10], myrank;
MPI_Status status;
// ...
MPI_Comm_rank(MPI_COMM_WORLD, &myrank);
if (myrank == 0) {
  MPI_Send(a, 10, MPI_INT, 1, 1, MPI_COMM_WORLD);
  MPI_Send(b, 10, MPI_INT, 1, 2, MPI_COMM_WORLD);
}else if (myrank == 1) {
  MPI_Recv(b, 10, MPI_INT, 0, 2, MPI_COMM_WORLD, &status);
  MPI_Recv(a, 10, MPI_INT, 0, 1, MPI_COMM_WORLD, &status);
}
// ...
```

> [!NOTE]
> Guarda i tag

Questo programma è corretto se send è non bloccante.

Se è implementata senza buffer, genera un deadlock, perché la prima receive aspetta la seconda send, e la prima send aspetta la seconda receive.

> [!TIP]
>Per evitare deadlock, le ricezioni devono essere nello stesso ordine degli invii.

### Esempio bad 2

```C
int a[10], b[10], P, r;
MPI_Status sts;
// ...
MPI_Comm_size(MPI_COMM_WORLD, &P);
MPI_Comm_rank(MPI_COMM_WORLD, &r);
MPI_Send(a, 10, MPI_INT, (r+1)%P, 1, MPI_COMM_WORLD);
MPI_Recv(b, 10, MPI_INT, (r-1+P)%P, 1, MPI_COMM_WORLD, &sts);
// ...
```

Se la send è unbuffered, questo programma genera deadlock.

Stesso discorso di prima su buffered e non bloccante.

> [!TIP]
> Evitare dipendenze circolari

Per rendere corretto il programma, si partizionano i processi (e.g. rank pari e dispari). Alcuni si comportano come prima, altri scambiano send e receive per rompere le dipendenze circolari.

```C
int a[10], b[10], P, r;
MPI_Status sts;
// ...
MPI_Comm_size(MPI_COMM_WORLD, &P);
MPI_Comm_rank(MPI_COMM_WORLD, &r);
if (r%2 == 1) { // r dispari
  MPI_Send(a, 10, MPI_INT, (r+1)%P, 1, MPI_COMM_WORLD);
  MPI_Recv(b, 10, MPI_INT, (r-1+P)%P, 1, MPI_COMM_WORLD, &sts);
} else { // r pari
  MPI_Recv(b, 10, MPI_INT, (r-1+P)%P, 1, MPI_COMM_WORLD, &sts);
  MPI_Send(a, 10, MPI_INT, (r+1)%P, 1, MPI_COMM_WORLD);
}
// ...
```

### Invio e ricezione simultanei

Per evitare situazioni come l'esempio precedente (esempio bad 2, dipendenze circolari), MPI fornisce una funzione speciale che combina send e receive.

```C
int MPI_Sendrecv(void *sendbuf, int sendcount,
                 MPI_Datatype senddatatype, int dest, int sendtag,
                 void *recvbuf, int recvcount,
                 MPI_Datatype recvdatatype, int source, int recvtag,
                 MPI_Comm comm, MPI_Status *status)
```

L'operazione è bloccante, svolge una send e una receive assieme. Gli argomenti sono la combinazione degli argomenti di send e receive.

### Esempio good 2

```C
int a[10], b[10], P, r;
MPI_Status status;
// ...
MPI_Comm_size(MPI_COMM_WORLD, &P);
MPI_Comm_rank(MPI_COMM_WORLD, &r);
MPI_Sendrecv(a, 10, MPI_INT, (r+1)%P, 1,
             b, 10, MPI_INT, (r-1+P)%P, 1,
             MPI_COMM_WORLD, &status);
// ...
```

È come l'esempio errato di prima, ma corretto usando sendreceive

### Variante di sendreceive

```C
int MPI_Sendrecv_replace(void *buf, int count,
                         MPI_Datatype datatype,
                         int dest, int sendtag,
                         int source, int recvtag,
                         MPI_Comm comm, MPI_Status *status)
```

È come sendreceive, ma invio e ricezione lavorano sullo stesso buffer. Ovvero i dati ricevuti sovrascrivono quelli inviati. Inoltre, il datatype e count è lo stesso tra send e receive.

È un po' più efficiente (meno memoria, meno copie).

### Invio non bloccante (isend)

Esistono le versioni non bloccanti di send e receive. Perché sono utili.

La I sta per immediate return. Perché la funzione termina subito senza aspettare il completamento.

```C
int MPI_Isend(void *buf, int count, MPI_Datatype datatype,
              int dest, int tag, MPI_Comm comm,
              MPI_Request *request)
```

La maggior parte dei parametri sono uguali a send. La differenza è il parametro `request` che permette di verificare se l'operazione è terminata.

Il processo chiamante deve evitare di modificare i dati in `buf` finché non sono stati spediti.

### Ricezione non bloccante (ireceive)

```C
int MPI_Irecv(void *buf, int count, MPI_Datatype datatype,
              int source, int tag, MPI_Comm comm,
              MPI_Request *request)
```

Anche qua gli stessi parametri di receive, tranne `request`.

Il processo non deve leggere i dati in `buf` finché la ricezione non è completata.

### Verificare lo stato delle operazioni non bloccanti

```C
int MPI_Test(MPI_Request *request, int *flag,
             MPI_Status *status)
```

Verifica se l'operazione associata a `request`. Il valore booleano di `flag` indica se l'operazione è terminata. Se non è terminata, il valore di status è undefined. Se è completata, a `request` viene assegnata la costante `MPI_REQUEST_NULL` (oltre ad assegnare il booleano `flag`).

A volte, verificare lo stato non basta, ed è necessario attendere il completamento di un'operazione:

```C
int MPI_Wait(MPI_Request *request, MPI_Status *status)
```

Questa funzione blocca il chiamante finché non è completata l'operazione descritta da `request`.

Alla terminazione, viene popolato `status`, e a request viene assegnato `MPI_REQUEST_NULL`.

Qualora non ci interessi lo stato di completamento di una operazione, possiamo deallocare l'oggetto `request` e lasciare che l'operazione prosegua in background normalmente. Viene fornita la funzione free:

```C
int MPI_Request_free(MPI_Request *request)
```

Quando una `request` è stata deallocata, non si può più fare ne test ne wait.

### Verificare lo stato di più operazioni (all)

A volte è necessario attendere più operazioni non bloccanti contemporaneamente

```C
int MPI_Waitall(int count, MPI_Request array_of_requests[],
                MPI_Status array_of_statuses[])
```

Similmente possiamo anche testare più operazioni contemporaneamente:

```C
int MPI_Testall(int count, MPI_Request array_of_requests[],
                int *flag, MPI_Status array_of_statuses[])
```

In questo caso `flag` sarà `true` solo se tutte le operazioni sono completate. Ed anche i due array saranno modificati solo se tutte le operazioni sono completate.

### Verificare lo stato di più operazioni (any)

Le due funzioni precedenti hanno una semantica tipo "all". Attendono/verificano *tutte* le operazioni. Spesso è utile aspettare/verificate una sola operazione qualsiasi tra un gruppo di operazioni. Una semantica tipo "any".

```C
int MPI_Waitany(int count, MPI_Request array_of_requests[],
                int *indx, MPI_Status *status)
int MPI_Testany(int count, MPI_Request array_of_requests[],
                int *indx, int *flag, MPI_Status *status)
```

Queste due funzioni attendono o verificano una qualsiasi tra `count` operazioni. La variabile `indx` indicherà quale operazione ha terminato.

## Operazioni collettive

MPI offre molte operazioni *collettive*, che coinvolgono tutti i processi di un domain. Viceversa, ogni processo del domain *deve* partecipare alle operazioni collettive.

In generale non implicano una barriera, quindi i processi non aspetteranno che tutto il domain abbia completato l'operazione. Rappresentano un punto di sincronizzazione virtuale, il programma dovrebbe essere scritto per funzionare correttamente anche se ci fosse una sincronizzazione prima e dopo l'operazione.

Lo standard impone che: se un processo invoca l'operazione collettiva X su on dominio, tutti i processi del dominio devono invocare X, e non possono invocare nessun'altra operazione collettiva (sullo stesso dominio) prima di X.

### Barriera

```C
int MPI_Barrier(MPI_Comm comm)
```

Blocca il chiamante finché tutti i processi del dominio non invocano la barriera.

Abbiamo detto che in genere le operazioni collettive non implicano una barriera implicita, e non sincronizzano i processi. Però alcune sì. Questa è un vero punto di sincronizzazione esplicito.

È poco usata, si usa principalmente per debugging, profiling, e i/o.

### Broadcast

```C
int MPI_Bcast(void *buf, int count,
              MPI_Datatype datatype,
              int source, MPI_Comm comm)
```

Deve essere eseguita da tutti i processi di `comm`. Spedisce un messaggio da `source` a tutti gli altri processi.

È bloccante nel senso che restituisce il controllo quando la semantica è garantita, ma non è detto che sia una barriera.

### Reduce

```C
int MPI_Reduce(void *sendbuf, void *recvbuf, int count,
               MPI_Datatype datatype, MPI_Op op,
               int target, MPI_Comm comm)
```

Effettua la riduzione N-to-1 dei valori in `sendbuf` contribuiti da ogni processo. Il risultato viene scritto in `recvbuf`, ma solo il processo `target` riceve la riduzione.

Le riduzioni sono eseguite "element wise": in `recvbuf[0]` sarà la riduzione di tutti i `sendbuf[0]`, in `recvbuf[1]` quelli di `sendbuf[1]`, etc.

Le operazioni sono:

| identificatore | operazione             |
| -------------- | ---------------------- |
| `MPI_MAX`      | Max                    |
| `MPI_MIN`      | Min                    |
| `MPI_SUM`      | Somma                  |
| `MPI_PROD`     | Prodotto               |
| `MPI_LAND`     | AND logico             |
| `MPI_BAND`     | AND bit-a-bit          |
| `MPI_LOR`      | OR logico              |
| `MPI_BOR`      | OR bit-a-bit           |
| `MPI_LXOR`     | XOR logico             |
| `MPI_BXOR`     | XOR bit-a-bit          |
| `MPI_MAXLOC`   | max-min value-location |
| `MPI_MINLOC`   | min-min value-location |

`MINLOC` e `MAXLOC` lavorano su coppie valore-indice invece che su singoli valori. Restituiscono la coppia col valore minimo/massimo, e rompono i pareggi controllando l'indice *minimo*. Nota bene che entrambe le funzioni usano l'indice minimo.

```C
int MPI_Allreduce(void *sendbuf, void *recvbuf,
                  int count, MPI_Datatype datatype,
                  MPI_Op op, MPI_Comm comm)
```

Effettua una riduzione N-to-N. Gli argomenti sono gli stessi, tranne `target` che manca. Tutti i processi ricevono il risultato della riduzione.

I tipi di dato su cui operano `MINLOC` e `MAXLOC` sono:

| identificatore        | tipo            |
| --------------------- | --------------- |
| `MPI_FLOAT_INT`       | `(float, int)`  |
| `MPI_DOUBLE_INT`      | `(double, int)` |
| `MPI_LONG_INT`        | `(long, int)`   |
| `MPI_2INT`            | `(int, int)`    |
| `MPI_SHORT_INT`       | `(short, int)`  |
| `MPI_LONG_DOUBLE_INT` | `(double, int)` |

#### Operazioni user defined

```C
int MPI_Op_create(MPI_User_function* user_fn,
                  int commute, MPI_Op* op)
```

Permette di creare un'operazione da impiegare in una riduzione. Il parametro `op` viene popolato con un handle, che si può passare alle funzioni reduce.

La funzione passata a `user_fn` deve avere firma:

```C
void user_fn(void* invec, void* inoutvec,
             int *len, MPI_Datatype *datatype)
```

In altre parole, il tipo `MPI_User_function` è definito come:

```C
typedef void (*MPI_User_function)(void*, void*, int*, MPI_Datatype*);
```

Si assume che l'operazione sia associativa (un monoide!). Mentre la commutatività si indica con il parametro `commute`, se è commutativa MPI può ignorare l'ordine di valutazione, altrimenti corrisponde al rank dei processi.

La funzione deve essere implementate in modo che per ogni `i` tra `0` e `len-1` si ha `inoutvec[i] = invec[i] OP inoutvec[i]`.

Si può deallocare un operatore usando:

```C
int MPI_Op_free(MPI_Op *op)
```

### Scan

```C
int MPI_Scan(const void* sendbuf, void* recvbuf,
             int count, MPI_Datatype datatype,
             MPI_Op op, MPI_Comm comm)
```

Prefix sum inclusiva in ordine di rank.

La funzione `MPI_Exscan` è uguale ma esclusiva.

### Gathering

```C
int MPI_Gather(const void* sendbuf, int sendcount,
               MPI_Datatype sendtype, void* recvbuf,
               int recvcount, MPI_Datatype recvtype,
               int root, MPI_Comm comm)
```

Permette di collezionare i valori spediti dai vari processi partecipanti. Deve essere chiamata in modo coerente da tutti i processi.

Tutti i processi (incluso `root`) inviano `sendbuf` al processo `root`. `recvcount` indica quanti dati root riceve da ogni processo, e generalmente `recvcount == sendcount`.

#### Varianti

```C
int MPI_Allgather(const void* sendbuf, int sendcount,
                  MPI_Datatype sendtype, void* recvbuf,
                  int recvcount, MPI_Datatype recvtype,
                  MPI_Comm comm)
```

Tutti i processi ricevono il risultato.

```C
int MPI_Gatherv(const void* sendbuf, int sendcount,
                MPI_Datatype sendtype, void* recvbuf,
                const int recvcounts[], const int displs[],
                MPI_Datatype recvtype, int root,
                MPI_Comm comm)
```

Permette di controllare il numero di elementi ricevuti (`recvcounts`), e la posizione nell'array (`displs`), dei dati ricevuti da ogni processo.

### Scattering

```C
int MPI_Scatter(const void* sendbuf, int sendcount,
                MPI_Datatype sendtype, void* recvbuf,
                int recvcount, MPI_Datatype recvtype,
                int root, MPI_Comm comm)
```

Distribuisce a tutti i processi una porzione dei dati inviati da `root`.

### All-to-all

```C
int MPI_Alltoall(const void* sendbuf, int sendcount,
                 MPI_Datatype sendtype, void* recvbuf,
                 int recvcount, MPI_Datatype recvtype,
                 MPI_Comm comm)
```

Combina gathering e scattering, come una variante di `MPI_Allgather`.

Per tutte le coppie di processi `i` e `j`, i dati inviati da `i` a `j` vengono memorizzati da `j` nella posizione `i`.

Esistono `MPI_Alltoallv` e `MPI_Alltoallw`.

### Esempio moltiplicazione matrice-vettore

```C
void RowMatrixVectorMultiply(int N, double *A, double *b,
                             double *x, MPI_Comm comm) {
  int i, j;
  int nlocal; // numero di righe di A accedute dal processo
  double *fb; // l’intero vettore b
  int P;
  // numero processi del gruppo
  MPI_Comm_size (comm, &P);
  // alloco spazio per tutto il vettore b
  fb = (double *)malloc(N*sizeof(double));
  nlocal = N/P; // assumo che N sia multiplo di P
  //colleziono le porzioni di b possedute da tutti i processi:
  MPI_Allgather(b, nlocal, MPI_DOUBLE, fb, nlocal, MPI_DOUBLE, comm);
  // eseguo la mia parte della moltiplicazione matrice-vettore
  for (i=0; i<nlocal; i++) {
    x[i] = 0.0;
    for (j=0; j<N; j++)
      x[i] += A[i*N+j] * fb[j];
  }
  free(fb);
}
```

## Gruppi e communicators

Un gruppo è un insieme ordinato di processi che il programmatore può gestire il gruppo tramite un handle.
In un gruppo, i processi sono identificati (e ordinati) dal rank, che è un numero da 0 a N-1 dove N è il numero di processi nel gruppo.

Ogni gruppo è associato ad un communicator, gestito tramite una handle. L'handle di tutti i processi è `MPI_COMM_WORLD`.

Dopo questa spiegazione, un gruppo e un domain sembrano la stessa cosa. La differenza è che il gruppo è l'insieme di processi, mentre il domain è il contesto. Un gruppo di processi comunica in un domain.
Allo stesso modo, l'handle di un gruppo è solo una lista di processi (non davvero, i tipi sono opachi), mentre il communicator mantiene l'handle e tutta una serie di dati aggiuntivi sul domain. Ovviamente questo lo spiega google, non il professore.

### Funzioni principali

```C
int MPI_Comm_group(MPI_Comm comm,
                   MPI_Group *group)
```

Ottiene l'handle del gruppo associato al communicator.

```C
int MPI_Group_incl(MPI_Group group, int n,
                   int *ranks, MPI_Group *newgroup)
```

Creazione di un nuovo gruppo che include i processi con i rank specificati in `rank`. Esiste anche `MPI_Group_excl`.

```C
int MPI_Comm_create(MPI_Comm comm,
                    MPI_Group group,
                    MPI_Comm *newcomm)
```

Crea un nuovo communicator per il sottogruppo `group` dei processi di `comm`.

```C
int MPI_Group_union(MPI_Group gr_a,
                    MPI_Group gr_b,
                    MPI_Group *gr_union)
```

Crea un gruppo come unione di due gruppi. Esistono anche `MPI_Group_difference` e `MPI_Group_intersection`.

```C
int MPI_Group_free(MPI_Group *group)
int MPI_Comm_free(MPI_Comm *comm)
```

Deallocano un gruppo o un communicator.

### Partizionamento di un communicator

```C
int MPI_Comm_split(MPI_Comm old_comm, int colour,
                   int key, MPI_Comm *new_comm)
```

Partiziona il gruppo associato ad `old_com`. Ogni processo esegue questa chiamata passando uno specifico `colour`, i processi con lo stesso colore vengono messi nello stesso gruppo. I processi ricevono il `new_com` del loro gruppo, ed i rank vengono stabiliti ordinando in base a `key` (disambiguando con il rank originale).

## Topologie virtuali

I processi sono ordinati linearmente tramite il rank.

In alcune situazioni è vantaggioso organizzare logicamente i processori secondo una topologia più complessa. Ricordiamo che anche in CUDA, a volte vuoi gli indici tridimensionali invece che lineari.

Ad esempio è utile riflettere qualche struttura e.g.:

* del problema
* dell'algoritmo
* dei dati
* dello schema di comunicazione
* dell'hardware

In MPI è possibile descrivere topologie diverse da quella lineare. Si possono identificare i processi con coordinate (anche a più dimensioni). Il mapping della topologia virtuale sui processori è dipendente dall'implementazione.

Idealmente, la topologia virtuale "facilita" il mapping.

### Topologia cartesiana

```C
int MPI_Cart_create(MPI_Comm comm_old, int ndims,
                    int *dims, int *periods,
                    int reorder, MPI_Comm *comm_cart)
```

Crea una topologia virtuale `comm_cart` per i processi di `comm_old`. Il numero di dimensioni è `ndims`, mentre `dims` indica la "lunghezza" in ciascuna dimensione.

`periods` indica se si ha periodicità in una delle dimensioni. Ovvero se l'ultimo elemento in quella dimensione è "connesso" al primo.

`reorder` indica se MPI può riassegnare i rank. Potrebbe migliorare il mapping o effettuare ottimizzazioni dipendenti dall'architettura, etc.

Ogni processo verrà identificato da un vettore di dimensione `ndims`.

#### Dimensioni

```C
int MPI_Dims_create(int numnodes, int numdims, int *dims)
```

Invece che calcolare manualmente i valori dell'array `dims` si può usare questa funzione. Si passa un array `dims` parzialmente popolato (alcuni valori sono nulli), MPI calcolerà i valori nulli tale che il prodotto delle dimensioni sia `numnodes`.

Lo scopo è quello di realizzare una topologia ottimizzata rispetto a quella fisica, nota all'implementazione.

#### Mapping

```C
int MPI_Cart_coords(MPI_Comm comm_cart, int rank,
                    int maxdims, int *coords)
int MPI_Cart_rank(MPI_Comm comm_cart,
                  int *coords, int *rank)
```

Queste funzioni permettono di mappare i rank alle coordinate e viceversa.

#### Shift

```C
int MPI_Cart_shift(MPI_Comm comm_cart, int dir,
                   int s_step, int *rank_source,
                   int *rank_dest)
```

Spesso  si vuole scambiare dati lungo una delle dimensioni (direzioni) della topologia, con un qualche stride.
Questa funzione permette di calcolare il rank lungo una dimensione.

Calcola `rank_source` e `rank_dest`, muovendosi dal rank del chiamante in stride di `s_step`, lungo la dimensione `dir`. Source viene calcolato muovendosi all'indietro e dest muovendosi in avanti.

Se la posizione di non esiste nella topologia, viene assegnato `MPI_PROC_NULL` al corrispondente `rank_source` o `rank_dest`. Se la dimensione è periodica si fa wrap around invece che assegnare rank nullo.

#### Partizioni di topologie

Si può partizionare una topologia cartesiana in sotto-topologie di dimensioni inferiori.

```C
int MPI_Cart_sub(MPI_Comm comm, int *remain_dims,
                 MPI_Comm* new_comm);
```

`remain_dims` è un array di booleani che indica lungo quali dimensioni si effettua la partizione. Quelle corrispondenti a true vengono preservate, quelle a false vengono partizionate.

Esempio: se si ha una topologia 3x4x5 partizionata con `[]{true, false, true}` si generano 4 sotto topologie 3x5.

Ogni processo ottiene il communicator della sua sotto-topologia in `new_comm`.
